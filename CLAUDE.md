# Spewboard: working rules

Shared rules for everyone working on this repo (and their Claude Code sessions, which read this
file automatically). Keep it short and current: if a PR changes a convention, update this file in
the same PR.

## The app and who decides

- **Spewboard** (repo still named PSSoundboard): an Android soundboard and voice FX app that plays
  sounds into any voice chat app on the phone (PlayStation App, Xbox, Discord, Teams, WhatsApp)
  through a 3.5 mm TRRS loopback cable.
- **Calum** (`calum176-maker`) owns the product and decides what it does. Ask before changing
  behaviour, naming or anything a user would notice beyond your issue.
- **`ROADMAP.md` is the source of truth** for features and direction. Suggestions and feedback that
  would change the app go in as a **Proposed** row; build only what Calum has marked **Approved**.
  Only Calum changes a status.
- AJ (`lt-flan`), Bryan (`lt-bryan`) and Steve (`lt-steve`) work on UI, UX and polish.
- Kotlin, Jetpack Compose, Material 3. minSdk 26, targetSdk 37.

## How we work

1. **One issue per task, one owner.** Before starting, find or open an issue and assign yourself.
   If someone else owns it, or your change touches files another open PR touches, say so on the
   issue first. Small issues beat big lanes.
2. **Branch and PR, never push to `main`.** Branch names: `fix/…`, `feature/…`, `ui/…`, `docs/…`,
   `ci/…`.
3. **Don't merge your own PR.** Someone else reviews it and tries it.
4. **Say how you tested it** (the PR template asks). "CI built it" is not a test of how it behaves.
   Without Android Studio you can still test: every PR's checks page has a `Spewboard-build-N` APK,
   signed with the shared key, that installs over the release build on your phone. Or ask AJ to run
   it on the emulator.
5. **PR titles are release notes.** Merged PR titles become the in-app "What's new" list and the
   GitHub release notes, so write them for testers ("Mini-deck: close it without going back to the
   app"). Start titles that testers wouldn't notice with `CI:`, `Build:` or `Docs:`; those are left
   out of What's new.

## Design rules

- **Use the shared pieces** in `ui/components/Playful.kt` (`PlayfulHeader`, `BlobChip`,
  `SpewButton`, `SoftButton`, `PlayfulField`, `StatusCard`, `PadLabel`, `IconBlobButton`,
  `CapsuleRow`) and `ui/theme/Blob.kt` (`Modifier.gummy`, `PadShape`). Icons come from
  `PlayfulIcons`. Don't add a one-off button or chip style.
- **Colours** come from `MaterialTheme.colorScheme`, or `MaterialTheme.spew` for app-only ones
  (`ui/theme/Theme.kt`). The only named colours to use directly are the fixed decorative palettes
  at the bottom of `Color.kt`. The `Slate*` and `Teal` names are legacy: don't use them in new code.
- **Type:** Bricolage Grotesque (`Bricolage`, `BricolageCondensed` in `Type.kt`).
- **Layout must survive** landscape (side rail, 6x2 pad grid) and a large system font (1.3x).
  Text inside pads goes through `PadLabel`, which shrinks names instead of breaking words. Never
  give a box holding text a fixed height.
- **The primary action** is the yellow `SpewButton`; red is only for stopping sounds.
- **Accessibility:** touch targets at least 48 dp; every icon-only control has a content
  description; pads expose one TalkBack action that matches what a tap does. Pads have no
  long-press (it's the Hold-mode gesture); editing goes through the Edit pads toggle.

## Wording

- **British English** in everything users read: colour, favourite, cancelled.
- **Sentence case** for titles, buttons and labels. No ALL CAPS, no Title Case, no emoji or symbol
  glyphs in button text (TalkBack reads them out).
- **"Spew" is the brand:** use it in headings, buttons and the Vault. Use plain words where people
  need to understand something fast: errors, permissions, notifications.
- **Say "voice chat"**, not "party" or "PS App"; the app isn't PlayStation-only.
- **The floating overlay is the "mini-deck"** (lower case mid-sentence).
- **Errors** say what didn't happen and what to do ("Couldn't play "Airhorn". Try again."). Log the
  exception; never show raw exception text.
- Steve's wording proposal on issue #3 is the reference for the rest, once Calum approves it.

## Don't

- **Don't change the application ID** `com.jms.pssoundboard`. Android would treat it as a different
  app: no updates, and everyone's decks are lost. Internal class names (`PSSoundboardApp`,
  `PSSoundboardTheme`) can stay too.
- **Don't break saved data.** `deck_state.json`, `spew_vault.json` and backup zips must keep loading
  in newer builds. If you change the format, read the old one too.
- **Don't commit** `local.properties`, keystores (`*.p12`, `*.jks`) or
  `app/src/main/assets/whats_new.json` (generated by the build).
- **Don't remove** `-Dorg.gradle.java.home` from the workflow, or the Windows JDK path from
  `gradle.properties` (local builds use it; CI overrides it).

## Builds and releases

- Every merge to `main` publishes a release; the newest APK is always at
  `releases/latest/download/Spewboard.apk`, and Obtainium picks it up.
- Version names are `1.0.N` and tags `v1.0.N`, where N is the workflow run number.
- Builds are signed with a shared test key (repo secrets `PSSB_KEYSTORE_B64`,
  `PSSB_KEYSTORE_PASSWORD`), so each build installs over the last without losing data.
- In-app feedback goes to the team's private Planka board (secrets `PSSB_FEEDBACK_URL`,
  `PSSB_FEEDBACK_KEY`). Builds without them fall back to the share sheet.
- Local build: `./gradlew assembleDebug lintDebug`. Lint must stay at 0 errors; don't add warnings.
